# Connectors

A team admin connects GitHub repositories and GitLab projects (up to 10 of each, each at an optional branch or tag) and one Jira project in Settings, under Connectors: Add connector offers GitHub repository, GitLab project and Jira project. Polaris reads every connected repository when it answers, searches code and checks facts, unless a question names one; sources name their repository (`dropsubs/website#7`, `dropsubs/infra!4` for a GitLab merge request). Each connector shows Connected, Not set up or Not reachable, checked live (`GET /settings/connectors`, one status per GitHub repository). Removing a row, and GitLab projects, go through `PUT /settings/connectors`.

## The demo world's connectors

The demo world's own repositories and Jira project exist only in the mocks, so they are always read from them: `MOCK_GITHUB_OWNERS` (e.g. `dropsubs`) names the GitHub owners whose repositories are read from `GITHUB_MCP_URL`, and `MOCK_JIRA_PROJECTS` (e.g. `DS`) the Jira project keys read and pushed through `JIRA_MCP_URL`. Connecting one of them asks for a token like any other, takes any token, and neither checks nor stores it. Leave both unset and nothing is treated as the demo's.

## GitHub repositories

An admin connects each repository with its own [fine-grained personal access token](https://github.com/settings/personal-access-tokens/new): Add connector, GitHub repository, then the repository (`owner/repo`, or a pasted link), an optional branch or tag and the token (`PUT /settings/github/repos`). The token needs only read access to that repository: Metadata, Contents, Issues, Pull requests and Commit statuses (classic `ghp_` tokens are refused). The brain asks GitHub's REST API (`GITHUB_API_URL`) whose token it is and checks that it reads the repository, naming any permission it lacks; nothing is saved otherwise. It stores the token encrypted with a key derived from `AUTH_SECRET` and never sends it to a browser. The row then shows `@login`. Each repository has its own token, so connecting one never depends on another. Edit changes the branch or the token (a blank token keeps the current one); Remove forgets the repository and its token.

Every read of that repository (answers, fact checks, code search, its status) goes to GitHub's hosted MCP server (`GITHUB_HOSTED_MCP_URL`, `https://api.githubcopilot.com/mcp/`) with its token as a bearer header, asking only for read-only tools; it never falls back to the mock. The hosted server is available to every GitHub account and needs no Copilot subscription. A token GitHub no longer accepts shows that repository as Not reachable, with the reason. A repository with no token (the demo world's, or one set through `PUT /settings/connectors`) is read from `GITHUB_MCP_URL` with no credentials. Tokens connected for a whole team before this were dropped by the `github_repo_tokens` migration: connect each repository again.

## The Jira project

An admin connects the team's Jira project with the account it is read and pushed with: Add connector, Jira project, then the site (`your-team.atlassian.net`), the project key, an Atlassian account's email and an [API token](https://id.atlassian.com/manage-profile/security/api-tokens) for it (a plain token, not one "with scopes") (`PUT /settings/jira/account`). The brain checks the account and the project with Jira before saving, calls only `https://<name>.atlassian.net`, stores the token encrypted with a key derived from `AUTH_SECRET` and never sends it to a browser. The project then becomes the one Polaris reads (answers, agenda suggestions, fact checks, caption keyterms), on its own site over Jira's REST API as that account, and its status is checked there. Remove forgets the account and the project (`DELETE /settings/jira/account`). A team has one Jira project; Edit replaces it. A demo project (`MOCK_JIRA_PROJECTS`) stays on the mock and keeps no account.

A team that connected a push account apart from the project Polaris reads, before the two were one, keeps both rows: the project is read through `JIRA_MCP_URL` and tasks are pushed to the account's project, until either is changed.

On a meeting's report, an admin then presses Push: each included draft becomes a Task in the account's project, as the connected account, with the meeting, the quoted moment and the approver in its description. The owner is assigned when Jira has exactly one assignable account with that person's email (or name); otherwise the issue is created unassigned and the page says so. A due date the project's create screen does not take is left out the same way. Each pushed task keeps the link to its issue. One push of a meeting runs at a time and each key is saved as soon as Jira has made the issue, so a retry after a failure creates only what is still missing. A project connected without an account (a demo project) is pushed to through the Jira MCP server (`JIRA_MCP_URL`), as the `brain push` CLI does; with no Jira project at all the board does not offer the push.
